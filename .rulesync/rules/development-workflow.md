## 开发与验证

- 安装依赖和验证改动时，在仓库根目录按 `README.md` 的「本地开发」说明选择适用的现有命令。
- 仅在用户明确要求时新增或修改测试。行为测试放在 `test/*.test.ts`，通过包名 `@zeta/reactivity` 导入公共 API。测试断言聚焦公共行为契约或已确认回归的可观察表现，避免绑定内部实现细节。
- 优先使用已有命令，从能够覆盖本次改动的最小、最快验证开始。纯文档或注释改动检查差异和适用的格式，行为改动运行相关现有测试。禁止为一次性检查编写测试文件或独立验证程序。
- 较窄的检查无法覆盖公共入口、编译输出或运行环境差异时，补做相应的构建或运行环境验证。检查范围随改动风险扩大。

## 提交与拉取请求

提交标题用中文或英文简要说明具体改动。拉取请求说明改动及其原因，列出实际执行的检查。涉及公共 API 或 npm 打包时，说明具体影响。有相关议题时附上链接。

## Agent 规则与工程知识维护

- `.rulesync/rules/` 只收录对后续任务持续有效、会改变 Agent 具体做法的仓库约定。优先记录 Agent 容易误判、违反后影响较大且难以由工具自动约束的规则。写清适用范围、需要保持的约束或必须执行的流程。
- 已有权威说明时，链接到该说明并指出查阅时机。仓库结构说明聚焦分类规则、职责边界和长期约束。
- 模块专属知识就近说明，面向使用者的用法优先放在 README 等已有文档。
- 更新规则前核对实际入口、配置和实现。规则与代码冲突时，先确认现行契约。合并重复条款，清理失效或已由工具强制执行的条款。临时规则写明移除条件。
- 修改规则源文件后运行 `npm run rules:generate`，将源文件和生成的根目录 `AGENTS.md` 一同提交。
