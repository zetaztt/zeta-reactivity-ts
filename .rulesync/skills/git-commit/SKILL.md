# 提交当前任务

单独调用 `$git-commit` 表示提交当前任务。用户指定的范围或“只写消息”等限定优先。先用 `git status --short` 区分已暂存、未暂存和未跟踪的改动。

- **只写消息**：将“给我一份提交日志”等拟稿请求按此模式处理。只读检查用户指定的范围。未指定范围时优先读取暂存区；暂存区为空时，按当前任务中能确定的变更拟稿。最终回复只包含一个纯文本代码块，内容为可直接复制的提交消息。
- **提交已暂存内容**：直接以 `git diff --cached` 为准，保留部分暂存文件的原有选择。暂存区为空时说明情况并结束。
- **提交本次任务**：结合任务上下文、已暂存和未暂存的差异判断归属，读取相关未跟踪文件的内容。暂存明确属于任务的路径或片段。若暂存区已有无关内容，或无法确定混合改动的边界，在变更暂存区前指出具体路径或片段，请用户决定。若没有可识别的任务，询问要提交的范围。

## 拟写提交消息

只写本次提交范围内的改动，遵循仓库提交规范。

标题用一行概括本次提交的主要内容。

需要正文时，标题后空一行，再用 `-` 列出主要改动事项，句末省略句号。

正文采用最小充分描述原则：

- 只描述做了什么，不解释具体实现。
- 使用直接、简短的工程术语，合并同类事项。
- 如果删除某个修饰词、限定条件或技术细节后，仍能准确表达主要改动，则删除它。
- 只有当具体细节本身就是改动重点，或省略后会产生实质性误解时，才予以保留。
- 不追求完整覆盖 Git 差异，不重复标题已表达的信息。

输出前检查是否还能删减文字而不损失主要改动事项。

## 执行提交

实际提交前，核对完整的 `git diff --cached`。

有可提交内容时执行本地 `git commit`，沿用现有 hooks 和签名配置。成功后用 `git log -1 --oneline` 和 `git status --short` 核对并报告结果；失败时说明 Git 给出的原因。推送和改写历史各自需要明确授权。
